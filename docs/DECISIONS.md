# Decisions

An append-only log — add to this, don't rewrite history in it. Each entry: what was decided, and why, so a later session doesn't quietly re-litigate something already settled for a reason that isn't obvious from the code alone.

## Settled

**Rewrite path: clean rewrite (Path C), not incremental upgrade or strangler pattern.**
Chosen after reviewing the dependency/risk assessment of the old app — the old app's `ng2-bootstrap` and `angular2-datatable` dependencies are structural to nearly every screen and both are effectively abandoned; combined with `@angular/http` (removed in Angular 8), duplicate/overlapping dependencies throughout `package.json`, and Angular CLI 1.x tooling, the gap was judged large enough that a rewrite was more predictable than a 14-major-version incremental path.

**No Angular Material.**
A `customer-list` scaffold was briefly built against Material (`MatTableModule`, etc.) as a first test, but the old app's `emqube-ui.css` design language represents months of deliberately tuned, working design. Decision: build thin standalone wrapper components (`EqTable`, `EqModal`, `EqDropdown`, etc.) that render the same `.eq-*` markup/classes, backed by CSS ported from the old app, rather than adopt Material's own visual system.

**Build order: Invoice List first.**
Not the simplest screen, but the most fully specified one — every filter, KPI calculation, status derivation, and two real backend endpoint bugs on it were already traced to the line during the old app's UI refresh work. Customer List was built only as an initial scaffolding test and is being discarded, not carried forward as "screen one."

**Knowledge base as multiple `/docs/*.md` files + root `CLAUDE.md`, not one giant file.**
Chosen for token efficiency: `CLAUDE.md` (auto-loaded by Claude Code every session) instructs reading `PROJECT-OVERVIEW.md`, `BUSINESS-RULES.md`, `CURRENT-WORK.md`, `API-NOTES.md` on every session; `ARCHITECTURE.md`, `UI-DESIGN-SYSTEM.md`, `DECISIONS.md` (this file), and `KNOWN-ISSUES.md` are read on demand, only when a task touches that area.

**`API-NOTES.md` vs `KNOWN-ISSUES.md` split.**
Nearly everything found in the old backend is simultaneously "how the API is shaped" and "a bug to route around" — kept as two files anyway, with a clear boundary: `API-NOTES.md` is the endpoint/shape reference (a look-up table); `KNOWN-ISSUES.md` is the running gotcha log (API-sourced or not — CSS traps, cascade bugs, etc. live there too). Avoids maintaining the same fact in two places by keeping the boundary intentional rather than incidental.

**User-area auth: direct `Common/GetLogin`, no SSO, keep the no-auth-header backend.**
User area implemented over the existing POST `{controller}/{action}` convention against the real backend. The new app's `auth-interceptor.ts` Bearer-token assumption is effectively dead code for now (the backend sends no auth header), but was left in place — the actual session is the `Login` payload stored as `localStorage.userDetails` and consumed via `UserService`. Central-login SSO (`Common/GetLoginCDB` + `/sso/validate-code`) is **not** ported yet; only direct username/password login. A route guard (`authGuard`) redirects unauthenticated users to `/login`.
- **Role-driven hide/show:** menu grouping + icons are **data-driven** from `Common/GetSiteuserMenuList(roleId)` → each `MenuModel` carries `MenuGroup` (`'Sales'`/`'Master Data'`) and `CssClass` (`icon-*`). `main-layout.ts` splits by `ParentMenu.MenuGroup === 'Sales'` (else Master), and `sidebar.ts` binds icons to `ParentMenu.CssClass` — the hardcoded name→group and name→icon maps were removed. **Confirmed role table (DB `Role`):** `1=Admin, 2=Manager, 3=Executive, 4=SuperAdmin`. Role 4 is **SuperAdmin, not Admin** — the earlier assumption that `roleId==4` meant "admin" was wrong. Menu visibility is `RoleId` → `MenuRole` rows only: Admin(1) & SuperAdmin(4) see the full set; Manager(2) sees only Sales (Invoice, Quote/Proforma); **Executive(3) has no MenuRole rows → empty sidebar** (data-driven, not a bug). In-page edit gating on Create/Edit Invoice mirrors the old app exactly: per-invoice `IsEditable === 1` **or** the logged-in user's `roleId === 4` (SuperAdmin) — the old gate is `[ngClass]="{'disabled': (IsEditable != 1 && roleId !=4)}"`, locked only when BOTH fail (re-added 2026-09-02; the `admin` user's `RoleId` is 1, and SuperAdmin 4 can always edit). The `RightView/RightCreate/RightEdit/RightDelete` menu flags are **NOT** used by either app's edit screen (they only exist on the menu model; the edit gate is `IsEditable` + roleId==4). The old app's cross-screen localStorage `IsEditable` hand-off is replaced by passing the list row's `IsEditable` through the edit route `editable` query param. **Copy** and **Print** are NOT permission-gated (only `IsCancel==false`), matching the old app — even a read-only locked invoice shows Copy + Print. The invoice **list** does not gate its row actions by role.

**Quotes are always editable — no `IsEditable` gating.** The old create-quote screen had no per-quote `IsEditable` lock (unlike invoices); the row div there has no disabled class. The new `/createquote` route therefore never renders read-only and takes no `editable` query param — Edit/Copy reachable by any role that can see the quote list.

**Quote VAT is one shared header-level code + discounted-pretax totals.** The old create-quote forces every line onto a single VAT code (`Product.VatCodeId = this.VatCodeId`) and computes the saved totals with the header-level discount applied to the pretax: `aggPreTax = sum(qty×rate) − discount`, `aggTax = aggPreTax×VATRate`, `aggTotal = aggPreTax+aggTax`. Ported exactly — quotes do **not** use the invoice's per-line-VAT/multi-code simplified logic, so the quoted totals can differ from the simple sum of per-line tax amounts whenever a discount is present (that's the old app's real behavior and the numbers the backend stores/reports).

**Improvements/bug-fixes log lives in `docs/IMPROVEMENT-LOG.html`, not in the MD docs.**
The user asked for a section-wise, functionality-focused record of what we did and why (areas: login, invoice list, edit invoice, copy invoice, quote list, edit quote, etc.), formatted for HTML browsing. `CURRENT-WORK.md` stays the terse day-to-day status; `IMPROVEMENT-LOG.html` is the human-readable what/why reference with matches to `MIGRATION-PLAN.html`'s styling. Keep its entries in the same "what we did + why" shape when adding new screens.

**Master Data is one generic config-driven page, not a screen per master table.**
A single component (`features/master/pages/master-data/`) serves every `MetaData` table, driven by the menu's `PageUrl` matrix params `{id,name}` and the DB `MetaData`/`MetaDataDetail` config — the grid columns, form fields and FK dropdowns are all derived from the backend's `GetMetaDataList`/`GetMetaData` responses, not hand-written per master. Reached from `/master,{id},{name}` (`main-layout.onMenuClick` already splits the comma `PageUrl`); `<nav>` is effectively unused/dropped (the sidebar drives navigation). Present-day three masters — Product(1), ProductCategory(2), PaymentTerm(3) — differ only in how many FK dropdowns and bit fields they carry, so one screen ports all of them. Security raises no extra concern here: there is no per-master auth, same as the old app (row actions are not role-gated). Bit columns render as Active/Inactive badges; the `Id` key column stays visible; search + pagination were added (the old master grid had neither). Product's `ProductType` FK dropdown lists every `Parameter` row (`WhereCondition=NULL`), which is the old app's behavior.

## Open — needs a decision before it matters

- **Auth mechanism for the new app.** The old app sends no Authorization header at all (role/user context is passed as plain values in the POST body); the new app's scaffolded `auth-interceptor.ts` currently assumes a Bearer token in `localStorage` that has no real counterpart today. Decide: keep calling the existing no-auth-header backend as-is for now, or is real token-based auth being added to the backend as part of (or alongside) this rewrite?
- **REST vs. existing POST-only convention.** The scaffolded `ApiService` uses `.get()`/`.put()`/`.delete()` against RESTful-looking paths; the real backend only exposes POST `{controller}/{action}` actions. Decide: adapt the new app's `ApiService` to match the existing convention (simplest, no backend change), or give the backend real REST routes as a parallel effort?
- **Icon system.** Old app uses simple-line-icons + a little Font Awesome. Keep both icon fonts, or move to inline SVG for the new app?
- **DB-driven menu grouping and icons.** The sidebar's "Sales" / "Master Data" grouping and per-item icon exist today only in the old app's client-side interim maps (see `KNOWN-ISSUES.md`) — a real fix means a DB column + SP + EDMX + mapping change. Not yet decided whether the new app repeats the interim-map pattern short-term or the DB change happens first.
