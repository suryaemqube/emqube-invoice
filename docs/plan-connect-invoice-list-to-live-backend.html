Connect Invoice List to Live Backend

Plan for wiring the new Angular app to the existing .NET backend and real database — updated August 2026

Problem

The Angular app's API configuration doesn't match the real backend. The app currently points to the wrong protocol, wrong port, and the auth interceptor sends a Bearer token header that the backend doesn't expect.

Configuration Mismatch
Setting Angular (environment.ts) Actual Backend Status
Protocol https:// http:// (IIS Express) Wrong
Port 5001 41728 Wrong
CORS Origin — http://localhost:4200 only OK if Angular on 4200
Auth header Sends Bearer {token} if present No auth enforced Unnecessary header
Content-Type application/json Expects application/json OK

Backend Architecture

The backend is a .NET Framework Web API project running on IIS Express. It uses Entity Framework 6 (database-first) to talk to a SQL Server database. There are two overlapping class libraries, but both point at the same physical database.

Implementation Steps

1
Fix environment.ts — API URL
Change the dev API URL to match the actual backend port and protocol. The backend runs on HTTP port 41728 via IIS Express, not HTTPS port 5001.
src/environments/environment.ts
Before: apiUrl: 'https://localhost:5001/api'
After: apiUrl: 'http://localhost:41728/api'

Why: The old backend's .csproj sets <IISUrl>http://localhost:41728/</IISUrl>. The old Angular app's http.service.ts confirms port 41728 as the dev URL.

2
Auth interceptor — no action needed
The existing authInterceptor sends Authorization: Bearer {token} only if a token exists in localStorage. Since there's no token, no header is sent. The interceptor is harmless and will be useful when real auth is added later.

Recommendation: Leave as-is. Don't remove it — it's future-proofing.

3
Confirm Angular dev server on port 4200
The backend's CORS is hardcoded to http://localhost:4200 in Web.config. Angular CLI defaults to port 4200.

Verify: Run ng serve and check the output shows Local: http://localhost:4200/. If port 4200 is occupied, Angular picks 4201+ and CORS will block it.

4
Start the backend
Open the old solution in Visual Studio and run the API project. 
1. Open: d:\projects\.net\01\emqubeinvoice2025\EmqubeInvoice\EmqubeInvoice.sln
2. Set EmqubeInvoice.API as startup project
3. Press F5 or Ctrl+F5
4. IIS Express starts on http://localhost:41728/

Verify: Browse to http://localhost:41728/api/Invoice/GetInvoiceList (POST with empty body) — should return a JSON array.

5
Handle CORS preflight
Angular (port 4200) → Backend (port 41728) triggers an OPTIONS preflight because Content-Type: application/json is a non-simple header.

The backend's Global.asax.cs handles OPTIONS requests and returns CORS headers. The headers returned are:

  • Access-Control-Allow-Origin: http://localhost:4200 (from Web.config)
  • Access-Control-Allow-Methods: GET, POST
  • Access-Control-Allow-Headers: Content-Type, Accept
  • Access-Control-Max-Age: 1728000

This is sufficient for our POST calls with Content-Type: application/json.

6
Test the connection
Start both servers and verify end-to-end data flow.
Test Checklist
  • Both servers running: Angular on 4200, backend on 41728
  • Navigate to http://localhost:4200/invoicelist
  • Open browser DevTools → Network tab
  • Verify: POST http://localhost:41728/api/Invoice/GetInvoiceList returns 200 with JSON array
  • Verify: Table populates with real invoice data
  • Verify: KPI cards show real outstanding/monthly totals
  • Verify: Year filter dropdown populated from Invoice/getInvoiceYear
  • Verify: Division filter dropdown populated from Invoice/GetBusinessDivisionList
  • Verify: Customer filter dropdown populated from Invoice/GetCustomerList
  • Verify: Free-text search filters the table
  • Verify: Status filter (Paid/Due/Cancelled) works
  • Verify: Pagination works (next/prev, page size change)
  • Verify: Record Payment modal opens with datepicker, min/max dates correct
  • Verify: Print Invoice opens PDF in new tab
  • Verify: Filter state persists across page navigation (localStorage)
7
Handle failures gracefully
If the backend is unreachable or returns errors, the app should degrade gracefully.
  • Backend not running: API calls fail with network error → InvoiceList sets loading = false, table shows empty state
  • Database unreachable: Backend returns 500 → same empty state behavior
  • Empty database: API returns [] → table shows "No invoices found" with Clear Filter button
  • CORS blocked: Browser blocks the request entirely → check console for CORS error, verify port and Web.config

Risks & Unknowns

⚠
Is the backend running locally? — If not, you'll need to set it up in Visual Studio or point to a remote server. The backend requires IIS Express and .NET Framework 4.x.
⚠
IIS Express port 41728 — This is set in the .csproj but AutoAssignPort is True. If you've opened the solution before on a different port, check the actual running port in IIS Express system tray or the Visual Studio output window.
⚠
Database connectivity — The backend needs a live connection to the EmqubeInvoice_UAT SQL Server. If the DB server is unreachable, all API calls will fail with 500 errors. Check the connection string in Web.config.
ℹ
Empty data — If the database has no invoices, the table will show the empty state. This is correct behavior — not a bug.
ℹ
Production URL — The old app uses http://invoice.emqube.net/api/ in production. The new app's environment.prod.ts uses https://api.emqube.com/api. Confirm which is correct before deploying.

Appendix: CORS Configuration

The backend has CORS configured at three overlapping layers:

Layer A: Web.config (IIS level)

<customHeaders>
  <add name="Access-Control-Allow-Origin" value="http://localhost:4200" />
  <add name="Access-Control-Allow-Methods" value="GET, POST, PUT, DELETE" />
  <add name="Access-Control-Allow-Headers" value="Origin, X-Requested-With, Content-Type, Accept" />
</customHeaders>

Layer B: Global.asax.cs (OPTIONS preflight handler)

if (HttpContext.Current.Request.HttpMethod == "OPTIONS")
{
    HttpContext.Current.Response.AddHeader("Cache-Control", "no-cache");
    HttpContext.Current.Response.AddHeader("Access-Control-Allow-Methods", "GET, POST");
    HttpContext.Current.Response.AddHeader("Access-Control-Allow-Headers", "Content-Type, Accept");
    HttpContext.Current.Response.AddHeader("Access-Control-Max-Age", "1728000");
    HttpContext.Current.Response.End();
}

Note: OPTIONS handler returns GET, POST only (not PUT/DELETE). This is sufficient for the Invoice List which only uses POST.

Layer C: WebApiConfig.cs (NuGet CORS middleware)

config.EnableCors();  // Enabled globally
// But [EnableCors] is commented out on controllers:
// [EnableCors(origins: "http://localhost:4200", headers: "*", methods: "*")]

The NuGet CORS middleware is enabled but no controller applies the attribute, so it's effectively inactive. All CORS is handled by Layers A + B.
