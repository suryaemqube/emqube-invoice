Improvements, Bug Fixes & Cleanup

What we did on the EmQube Invoice rewrite, and why — organised by functional area (functionality-wise).

Status as of 2026-09-02  Complements docs/CURRENT-WORK.md / DECISIONS.md

This is the running log of improvements, bug fixes and cleanup made while porting the legacy app to the new Angular app. Every entry records what was done (functionality-wise) and why it was done — either to match the old app's real behaviour, or to fix something that was broken or misleading. It does not re-describe screens that are straight ports; only the meaningful changes and the reasoning behind them.

1.Login

Improvement Branded logo on the login screen
What

Replaced the plain "EmQube" text brand with the actual logo image (<img src="/media/emqube-logo-black.svg">, served from a copy under public/media/).

Why

Brand presence on the entry screen, consistent with the company identity the old app used.

Improvement White login background
What

Login page background changed from the default grey to white (var(--eq-surface)).

Why

Cleaner look against the auth layout; visually consistent with the rest of the app's surfaces.

Improvement Show / hide password toggle
What

Added an eye toggle (fa-eye / fa-eye-slash) behind a .eq-password-wrap + .eq-password-toggle button that switches the password field between type="password" and type="text".

Why

Passwords are typed on a touch display / shared screens; letting the user verify what they typed reduces login failures. Also mirrors the same pattern used on the Change Password page.

Improvement Compact, right-aligned Sign In button
What

Sign In is now the shared eq-btn-sm variant and right-aligned on the card.

Why

Tighter visual rhythm on the card; the large full-width button was over-bearing for a single-field form.

Improvement Login inputs use the shared field style
What

The global _forms.scss .eq-field rule was extended to include input[type="password"] and input[type="email"], so the login (and change password) inputs now use the exact same styling as the create/edit invoice fields — 38px tall, 13.5px text, --eq-border, radius, and the primary focus ring.

Why

Before this, login fields looked subtly different from every other form field in the app. One shared source of truth instead of a duplicated bespoke style.

2.Change Password

Improvement Old-password field added
What

The form now has an Old Password field in addition to New / Confirm, and all three fields get their own independent eye toggle.

Why

The backend ChangePasswordModel / SP ChangePassword(userId, OldPassword, NewPassword) requires the old password (it is encrypted server-side). Without the field the request could not be built to the real contract, and a change could silently fail the old-password check.

Improvement Payload now matches the backend
What

POST Common/ChangePassword sends { userId: profileId, OldPassword, NewPassword, ConfirmPassword } and validates old + new entered and new == confirm before submitting.

Why

Matches the real backend contract exactly; client-side validation avoids round-trips for the most common mistakes.

3.Session & auth

Design Session = the login payload, not a token
What

UserService + core/models/user.model.ts describe the session. The authed session is the Login payload stored as localStorage.userDetails; an authGuard redirects unauthenticated users back to /login.

Why

The backend sends no Authorization header at all — role/user context is passed as plain body values, so the login payload is the session. The scaffolded Bearer-token interceptor is effectively dead code for now and was left in place rather than wired to something that doesn't exist.

Scope Direct Common/GetLogin only (no SSO)
What

Only the direct username/password path is ported. The central-login SSO flow (Common/GetLoginCDB + /sso/validate-code) is not ported.

Why

Deliberate scope decision (recorded in DECISIONS.md) — the direct path is what the old app actually runs day-to-day; SSO needs its own separate, explicitly-requested effort.

4.Role-driven menu & sidebar

Improvement Menu grouping & icons are now data-driven
What

main-layout.ts splits Sales vs Master menus by the real ParentMenu.MenuGroup === 'Sales' flag from Common/GetSiteuserMenuList(roleId), and sidebar.ts binds icons to the API's ParentMenu.CssClass. The hardcoded name→group and name→icon maps were deleted.

Why

Previously any DB menu change (new menu, renamed menu, new icon) required a frontend code change. Now the sidebar is a pure reflection of the data, so it can't drift from the backend.

Bug fix Executive / empty-role sidebar hidden
What

Confirmed the real role table: 1=Admin, 2=Manager, 3=Executive, 4=SuperAdmin (Role 4 is SuperAdmin, not Admin). Executive (Role 3) has no MenuRole rows → empty menu. When a role has no menus the hamburger button, <aside> sidebar and mobile backdrop are all removed from the DOM via @if (hasMenus), and a body.eq-no-sidebar class makes .eq-main/.eq-footer full-width (brand width anchored at 160px).

Why

An executive logging in used to land on a broken empty shell with a dangling hamburger and a dead sidebar. Now the content area simply takes the full width — a clean, usable screen for a role with no menus.

Bug fix No dangling group titles on empty groups
What

Both SALES and MASTER DATA section titles are now wrapped in @if (…), so an empty group renders no header at all.

Why

Roles with Sales-only menus (e.g. Manager) previously showed a meaningless empty "MASTER DATA" title; roles with nothing showed an orphaned title.

Important context: the earlier assumption that roleId == 4 meant "admin" was wrong and was actively dangerous for edit-gating logic (see §10). Role 4 is SuperAdmin; the actual admin user has RoleId 1.

5.Profile menu (login time)

Improvement Last-login shown in the profile dropdown
What

A login-time pull-left span now sits inside the profile menu header as a direct child on its own row (flex row, top-border separator). The loginTime getter formats LastLogin as d/M/yyyy, h:mm:ss am/pm, and the span only renders when the value exists.

Why

Shows the real last-login info the old app kept, without cluttering the main header — useful when a shared machine was used by someone else.

6.UAT / LIVE runtime config

Improvement Runtime API URL switching via config.json
What

public/config.json holds { apiUrl, fileBaseUrl }. A new ConfigService (core/services/config.service.ts) loads it at bootstrap through an APP_INITIALIZER wired in app.config.ts. ApiService.post now targets configService.apiUrl, and both print consumers (invoice-list.ts, create-invoice.ts) open generated PDFs from configService.fileBaseUrl (/Documents/Invoice/{file}, /Documents/Quote/{file}). Falls back to environment.apiUrl if the file is missing.

Why

The same build now targets UAT or LIVE just by deploying a different config.json — no rebuild per environment. Print URLs need the file base because the API returns only a file name/path, not a full URL.

7.Invoice List

Bug fix KPI cards under-counted new invoices
What

KPIs previously parsed InvoiceDateString — the d/M/yyyy display string — with new Date(), which fails on that format. They now parse the ISO InvoiceDate (falling back to the string), exactly like the old app (which parses item.InvoiceDate for KPI math and uses the string only for display). Same fix applied to PaymentRecdDate for "Paid this month". Unused extractYear() removed.

Why

Newly created/copied invoices silently vanished from "Invoiced this month" and "Outstanding (YR)" because their date string could not be parsed. The numbers now count real invoices.

Improvement Outstanding KPI converts to AED at the invoice's saved rate
What

"Outstanding (YR …)" now sums InvoiceTotal × (ConversionRate || 1) over non-cancelled, unpaid, same-year invoices. The backend list already returns per-row ConversionRate; the field was added to the frontend InvoiceListModel to consume it.

Why

USD (or any other-currency) invoices were being summed raw against AED invoices, so the card was wrong for any shop with foreign-currency invoices. Converting at the rate recorded on the invoice matches the business rule that each invoice's rate is fixed at creation.

Cleanup Endpoint hygiene on the list
What

The new list calls the real Invoice/GetCustomerList. The old invoicelist.component.ts called Invoice/GetCustomers — which does not exist — for months and it only surfaced when the feature was actually wired up.

Why

Don't carry a dormant, broken call into the rewrite. Every endpoint is checked against the real controller source before being built around (see KNOWN-ISSUES.md).

Also present (straight ports, no change of behaviour): search + Year/Status/Division/Customer filter toolbar with clear button, KPI cards, 9-column table with inline status badges and division icons, action dropdown (Edit always, Record Payment for due invoices, Print for non-cancelled), pagination (50/100/150), empty state, skeleton loading, and filter persistence via localStorage (saved on change, restored once then deleted).

8.Create / Edit Invoice

Bug fix Loader freeze — form stuck on "Loading invoice form…"
What

Root cause was change detection not re-rendering after loading=false even though all 13 boot endpoints returned 200. Forced with ChangeDetectorRef.detectChanges() in the forkJoin next/error handlers and in loadInvoice(). Also added per-group timeout(15000) + catchError → of(null) and a 30s safety cap.

Why

The screen could be permanently stuck on loading for no real reason. The fallbacks also make one slow/failed master-data endpoint degrade gracefully instead of blocking the whole form.

Bug fix Edit-load showed €0.00 / wrong status (VAT-code mapping)
What

The backend DTO sends VATCodeId (capital), but the model read VatCodeId. Every loaded line's VAT code became 0, calculateTax() skipped all lines, totals stayed 0, and the status badge fell into the "Cancelled" heuristic (InvoiceTotal == 0 && TotalVAT == 0). Fixed in normalizeRow() to read VATCodeId ?? VatCodeId, with an InvoiceVatRate fallback for the rate.

Why

Editing any saved invoice silently showed zeroed totals and a wrong status badge. This was the exact kind of "same name, different casing" bug the docs warn about — the frontend model and the backend DTO disagreed.

Bug fix Cancelled invoices resurrected as "Paid"
What

cancelledOnLoad is now captured from the backend header (InvoiceTotal==0 && TotalVAT==0) before calculateTax() runs, and isCancelled uses it for loaded invoices.

Why

calculateTax() recomputes totals from line Qty × Rate on load, which resurrected non-zero totals on a cancelled invoice → it showed "Paid" and exposed the Copy button. New and copy invoices are never treated as cancelled.

Improvement Header meta mirrors the old screen
What

Edit mode now shows Paid/Due/Cancelled badge · Customer Name · Invoiced {date} · Read-only badge, driven by the invoiceDateLabel getter. Back button reads "Back to Invoices".

Why

At-a-glance status and context without opening the form; matches the old screen's information density.

Improvement Payment date is not auto-computed
What

Removed applyPaymentDate() auto-fill from onInvoiceDatePicked / onPaymentTermPicked. Payment date is only set when the user picks it (or parsed from the stored value on edit-load). Bounds relaxed to the global invoice-date range (2017-06-10 → today).

Why

The old app's SetPaymentDate() is defined but never invoked, and its payment-date input has no change handler — so the old app never filled it automatically either. Matching the real behaviour beats adding invisible magic that would change saved data.

Improvement Line table no longer forces page scroll
What

Removed the fixed <colgroup> pixel widths; set min-width: 0 + table-layout: auto locally, and reused the old num/actions column classes.

Why

The fixed widths made the table wider than the viewport and pushed the whole page into horizontal scroll.

Also present (faithful ports): new quote pre-fill from the customer-quote selector; edit-load via GetInvoicesList with back-solved discount mode; per-line discount (percent/flat) with live tax recalc; VAT-code-grouped summary under the grid; faithful tax math for both the standard and simplified (IsTaxInclusive || VATType === 1) branches; TinyMCE terms editor; save posts the whole form to the (misspelled, kept as-is) AddUpdateInvoive endpoint → toast + redirect.

9.Copy Invoice

Improvement In-page copy (no route change)
What

Header Copy button on the edit page (isEdit && !isCancelled && !isCopy) opens an ng-bootstrap confirm modal; Yes → copyInvoice(): sets isCopy=true, nulls TaxInvoiceId, InvoiceNumber, and the Invoice/Delivery/Payment dates, and zeroes each line's TAXInvoiceDetailId/TaxInvoiceId. Customer, lines and footer text are kept. Saving then posts to the same AddUpdateInvoive endpoint and the backend creates a brand-new invoice.

Why

Matches the old app's copy semantics (same screen, data kept for review, new ids on save) without a localStorage hand-off flag. A real copy is more useful than a blank form because it starts from the edited source data.

Improvement Copy clears all dates, incl. payment
What

form.Payment*, paymentDateStruct and the other date fields are all nulled, and a setTimeout(cdr.detectChanges()) makes the datepicker inputs visibly clear after the modal closes.

Why

The user should re-date the copy. Matches the old app, which also nulls the payment date in CopyItem.

Bug fix Copy blocked for cancelled invoices
What

The Copy button is hidden and copyInvoice() guards on isCancelled.

Why

Copying a cancelled (then resurrected-totals) invoice was the symptom of the status bug in §8; once status is correct, copying a cancelled invoice is meaningless.

10.Edit gating (read-only view)

Design Per-invoice read-only, not per-role
What

canEdit = invoiceEditable === 1 for saved edits (new/copy drafts always editable). The invoice list passes the row's IsEditable to the edit route via the editable query param (this replaces the old app's async localStorage.IsEditable hand-off). Default is 0, so an edit reached without an explicit editable=1 renders read-only. The eq-readonly class locks the form layout (pointer-events:none, re-enabling .eq-summary-actions); Save + Cancel Invoice are hidden when !canEdit, while Copy (header) and Print (summary) stay available.

Why

Mirrors the old app exactly: a locked invoice (IsEditable != 1) is a read-only view regardless of who is logged in. Copy/Print are not permission-gated (only IsCancel==false) — same as the old app. The roleId == 4 always-edit branch was dropped: the admin's real RoleId is 1, so the only thing that ever unlocks a locked invoice is IsEditable == 1 itself.

11.Quote List

Bug fix (avoided) Real field is InvoiceRevNumber
What

QuoteListModel.InvoiceRevNumber (string) is the real field. The old template rendered {{row.QuoteRevNumber}}, which doesn't exist on the model — an old-app bug we did not port. (It is simply not rendered; the model carries the real field.)

Why

Rendering an undefined field would show undefined/empty in the new grid; the actual revision number lives in InvoiceRevNumber.

Bug fix (avoided) No Invoice/GetCustomers call
What

The old quotelist.component.ts calls the non-existent Invoice/GetCustomers (real: Invoice/GetCustomerList) — the same bug as the old invoice list, still unfixed there. The new quote list does not call it at all.

Why

Same endpoint-hygiene rule as §7: never build a service around an action the controller doesn't expose.

Improvement Division / Customer / Type filters added
What

The quote list now has Division, Customer and Type filter dropdowns alongside Year and search. Options are derived client-side from the loaded list (divisionOptions/customerOptions/typeOptions computed signals over distinct DivisionName/CustomerName/QuotetypeText values), applied in filteredList, and persisted in the same QuoteFilters localStorage blob as the year/query.

Why

The old quote list had no such filters (only search), but the backend list already returns all three fields, so filtering client-side is free and matches the invoice list's filter model.

Bug fix Date column collapsed on later pages
What

On page 2 the Date column shrunk and 10-01-2025 wrapped over 3 lines. Cause: .eq-table uses table-layout: auto, so column widths are recomputed from each page's visible rows — a different page's content re-balanced the columns and squeezed the date. Fixed by making the date cell non-wrapping (.eq-table td.eq-nowrap { white-space: nowrap } in quote-list.scss) and giving the Date column a width: '90px' hint.

Why

A dates column is short fixed-width content; allowing the auto-layout to shove it down below its own text width is the whole bug. With a nowrap cell the column can never shrink below the date's width on any page.

Improvement Type moved inline with the quote number
What

The standalone Type column was removed; the type now renders next to the number in the first cell — <span class="eq-mono">2026-43 <small> - Proforma</small></span> — one column freed up and the grid reads tighter. The Type filter is unaffected (it filters on QuotetypeText regardless of where it renders).

Why

A whole column for a 1-word value wasted horizontal space on a 10-column table; the number+type combo is compact and keeps the same information visible.

Also present (straight port): search + Year toolbar, no KPI cards (the old quote list has none), paginated table (default 100, 50/100/150), skeleton loading, empty state, QuoteFilters localStorage persistence (year + query + division + customer + type), columns for number+type / date / customer-link / value / tax / division / product / sales executive, and row actions: Edit → /createquote/:id, Copy → /createquote/:id?copy=1, Print → Invoice/GenerateQuote → /Documents/Quote/{file} via ConfigService.fileBaseUrl.

12.Create / Edit Quote

Improvement Revisions table uses the real field
What

The revisions card (loaded via Invoice/getQuoteRevisions) shows Version = rev.QuoteNumber and Date = rev.CreatedOn (formatted), with a per-version Print PDF action. The old app concatenated {{item.QuoteNumber}}{{item.QuoteRevNumber}} — but the backend QuoteRevisionModel has no QuoteRevNumber field, so the old screen rendered garbage like Q-0001undefined.

Why

Faithful-to-intent but not faithful-to-bug: we show what the old screen meant (version + date + pdf), using a field that actually exists.

Design Quote VAT & totals follow the quote formula, not the invoice formula
What

Quotes use a single shared VAT code across all lines (one header select), a header-level discount (percent or flat), and the saved totals are computed on the discounted pretax: aggPreTax = sum(qty×rate) − discount, aggTax = aggPreTax × VATRate, aggTotal = aggPreTax + aggTax. No tax-inclusive / simplified math. This exactly matches the old create-quote's CalculateTaxAmount(), which differs from the invoice branch.

Why

The numbers the backend stores and reports are these discounted-pretax totals. A "cleaner" invoice-style calculation would change saved values for any quote with a discount — a silent behavioural regression.

Design Quotes are always editable
What

The create-quote page has no read-only mode and no editable query param; the Quote/Proforma radio re-enables in copy mode.

Why

The old create-quote screen had no per-quote IsEditable lock (unlike invoices), so there is nothing to gate on — copying the invoice gating here would invent a restriction the old app doesn't have.

Improvement Copy uses the same in-page pattern as invoices
What

Header Copy button (edit mode only) → confirm modal → copyQuote(): isCopy=true, QuoteId/QuoteNumber/QuoteRevNumber nulled, per-line QuoteDetailIds nulled, toast. The list's ?copy=1 route does the same thing on load. Saving posts the whole form to Invoice/AddUpdateQuote and the backend assigns a new quote.

Why

Mirror the old app's localStorage invoiceIdcopy flag — but via the route/query param the list already passes, so no cross-screen global state.

Also present (faithful port): Quote/Proforma radio (disabled on saved quotes), customer select auto-fill, read-only quote no. (QuoteNumber + QuoteRevNumber), LPO, date, currency → read-only rate, payment terms (default 4), quote/proforma type, sales executive, division, place of supply, shared VAT code, line items (product pick → description/UOM autofill, no per-line discount column — the old quote dropped it), discount row in the line-summary table, AED + "Base (AED)" conversion columns, TinyMCE terms, summary card (Pre Tax / VAT / Total + foreign-currency block), save validation toasts.
Improvement "Show total" toggle restored (prints totals only when on)
What

A Show total switch now sits below the Items summary table (the old app had exactly this switch there, bound to InvoiceData.showtotal, default true). Backed by a new QuoteModel.showtotal field: default true, loaded from the saved quote, saved with it via AddUpdateQuote.

Why

It controls the printed PDF, not the screen: the backend GenerateQuote (InvoiceService.cs:964,1251,1278,1323,1335) hides the Totals row, the amount in words, the "Total Payable (currency)" cell and the Taxable-Value/VAT payable table whenever showtotal is false. The old screen's switch was functional and the flag is stored per quote, so our port had silently dropped a real feature — now restored and saved.

Bug fix VAT dropdown showed duplicated text
What

Option text was {{ VATCodeName }} {{ VATRate }}%, but the backend's VATCodeName already contains the rate (e.g. 5%, 0%, Exempt 0%), so the dropdown displayed 5%  5%, 0% 0%, Exempt 0%. Now shows just {{ VATCodeName }} in both the Document Details VAT select and the per-line VAT select — matching the old app's single {{VATCode.VATCodeName}}.

Why

The duplicated text was the exact "two things with the same meaning, rendered doubled" trap: the code re-appended a rate the name already carried. Display now matches what the old screen showed. (The create-invoice page had the same doubled pattern — fixed identically on 2026-09-02.)

13.Customer List

New screen Customer list + add/edit modal (port)
What

Built the Customer screen as a single page with a list and an add/edit modal, matching the old customer.component.* (which had no separate create page either). Routes /customerlist (the menu's PageUrl) and the leftover /customer both load the real component now (both were placeholders). New features/customers/ folder with services/customer.service.ts (GetCustomerList / GetCustomer / AddCustomer / GetCountry / GetState / GetCurrencyList) and models mirroring the backend CustomerListModel / CustomerModel / AddressModel.

Why

Completes the Sales-area screens started by the invoice/quote lists. The customer list and modal reuse the existing EqTable/EqPaginator/EqBadge/EqToolbar and the already-scaffolded _customers.scss (switch + type-badge CSS) rather than the old mfDataTable/bsModal libraries.

Bug fix Customer select bound to the right endpoint
What

The new service uses Invoice/GetCustomerList (the real endpoint) for both the list and the modal, and Invoice/GetCustomer for the edit-modal fetch. The old invoice/quote lists' habit of calling the non-existent Invoice/GetCustomers was not repeated here.

Why

Same endpoint-hygiene rule as §7/§11: never build a service around an action the controller doesn't expose.

Bug fix (avoided) "Same as billing" toggle handling
What

On add, shippingAddressSame defaults to true so the shipping fields are hidden and on save the shipping address isn't required. On edit, it loads whatever shipping address the customer has and shows the fields. Toggling the switch on copies Billing into Shipping with AddressId=0, exactly like the old onCheckBoxChange().

Why

The old app always set shippingAddress = false on editItem() even when shipping was never filled in; ours shows the real stored values instead. The add-path behaviour (same-as-billing by default) matches the old screen.

Bug fix Currency "null" string trap
What

The old template used the string value="null" for the "select currency" placeholder and the validator compared against the string "null". In the new modal the placeholder is a real [ngValue]="null" and the validator checks actual null — no string-conversion foot-gun.

Why

The string form was a coercion trap (an untouched "Select Currency" would send the literal string "null" to the backend). Angular's [ngValue] binding models it correctly.

14.Shared building blocks

Design Thin .eq-* wrappers instead of Angular Material
What

Built EqBadge, EqToolbar, EqDropdown, EqPaginator, EqTable (skeleton loading) and ToastService as small standalone wrapper components over the shared .eq-* CSS classes.

Why

The old app's design language is months of tuned CSS; Material would have replaced it wholesale. Thin wrappers give reuse across list and form screens while keeping the exact same visual system (per DECISIONS.md).

16.URLs & navigation — how edit/copy links work

The number in /createinvoice/31284?editable=0 or /createquote/313 is not random — it is the clicked row's TaxInvoiceId. This section is the reference for how those links are built and what happens if you change or remove parts of them.

URLBehaviour
/createquoteNew blank quote / proforma
/createquote/313Edit quote #313 — loads that record from the backend
/createquote/313?copy=1Copy of quote #313 — quote id, number and line ids reset for a fresh save
/createinvoiceNew blank invoice
/createinvoice/31284Edit invoice #31284 — read-only by default (no editable param)
/createinvoice/31284?editable=1Edit invoice #31284, writable
/createinvoice/31284?editable=0Edit invoice #31284, read-only (Save / Cancel hidden; Copy + Print stay)
How it works Where the number comes from
What

Both lists navigate with the row's TaxInvoiceId as the :id route segment: quote list → router.navigate(['/createquote', row.TaxInvoiceId]) (quote-list.ts:166, Copy adds ?copy=1), invoice list → router.navigate(['/createinvoice', row.TaxInvoiceId], { queryParams: { editable: row.IsEditable === 1 ? 1 : 0 } }) (invoice-list.ts:296). The create pages read route.snapshot.paramMap.get('id') in ngOnInit: present → edit mode (loads that record from the backend); absent → new blank form.

Why

This is the route-param alternative to the old app's cross-screen localStorage hand-offs (invoiceIdcopy, invoiceId): no global state, and a URL is shareable/bookmarkable. The id is the database key (QuoteId / TaxInvoiceId) the page passes straight to getQuotesList(id) / getInvoicesList(id).

How it works What editable=0 does
What

It carries the invoice's IsEditable flag from the list. create-invoice.ts:180-183 turns editable=1 into invoiceEditable=1, anything else into 0; canEdit = invoiceEditable === 1. So editable=0 → read-only view (Save + Cancel hidden, Copy + Print still available). Quotes carry no such param — they are always editable (see §10/§12).

Why

Matches the old app's hand-off of a locked invoice (IsEditable != 1) as a read-only view. The default is 0 so an edit reached without an explicit editable=1 renders read-only — a locked invoice can't be unlocked by hand-editing the URL.

What if you remove parts of the URL?
  • Removing ?editable=0 → the param is null, the branch is skipped and invoiceEditable keeps its default 0. No break — same read-only behaviour.
  • Removing the number (/createinvoice or /createquote) → no :id, so the page opens a new, blank document instead of the existing one.
  • A wrong/unknown id simply loads that id; if the backend returns nothing the page falls back to a new/default form — it does not crash.
