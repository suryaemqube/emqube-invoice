# Known Issues

Real bugs and gotchas already found in the old codebase — confirmed by tracing actual code, not suspected. Check here before assuming an endpoint, field, or CSS rule behaves the way its name suggests.

## Backend / API

- **`Invoice/GetCustomers` doesn't exist.** `invoicelist.component.ts` called it for an unknown amount of time with no effect (the feature using it was dormant until recently). The real endpoint is `Invoice/GetCustomerList`. This was fixed in the old app's `invoicelist.component.ts`; **`Quote/quotelist/quotelist.component.ts` has the identical bug, still unfixed.**
- **Two unrelated classes are both named `GetSiteUserMenu_Result.cs`** — one in `EmqubeInvoice.DAL` (dead code for this purpose), one in `emQubeLibrary` (the real one, feeding `LibraryEntity.Context.cs`). Editing the wrong one compiles fine and does nothing. See `ARCHITECTURE.md`.
- **`MenuItem` already carries `CssClass` AND `MenuGroup` in the DB, and both DO reach the client** — this was previously mis-documented as "the SP doesn't select them". Confirm with real data (`MenuItem` table: `MenuGroup` is `'Sales'` or `'Master Data'`, `CssClass` is e.g. `icon-doc`): `emQubeLibrary/GetSiteUserMenu_Result.cs` declares both columns, and `emQubeLibrary/EmqubeCommonService.GetSiteuserMenuList(int roleId)` copies `dt.CssClass`/`dt.MenuGroup` into every `MenuModel`. So the old app's hardcoded `menuIcons` map + name-based `buildMenuGroups()` in `full-layout.component.ts` are **unnecessary** (the stale comment there that "the SP doesn't return CssClass" is wrong for the emQubeLibrary context — the *other* `GetSiteUserMenu_Result.cs` in `EmqubeInvoice.DAL` is the one that's dead code for this path, see the note above). The new app was patched (2026-09-01) to be data-driven: `buildMenuGroups()` splits by `ParentMenu.MenuGroup` (`Sales` vs `Master Data`) and the sidebar binds icons to `ParentMenu.CssClass` — the hardcoded maps were removed from `main-layout.ts`/`sidebar.ts`.
- **`localStorage` key typo in the old invoice list.** `invoicelist.component.ts` reads `localStorage.getItem("userDetail")` (singular) while every other screen writes/reads `"userDetails"` (plural) — so the invoice list's `userDetail` is always null and any per-screen role read there silently fails. The new app uses one consistent key (`userDetails`) everywhere via `UserService`.
- **`IsEditable` crosses screens via `localStorage`, not the API.** The old app's invoice list stores a per-row `IsEditable` into `localStorage` before navigating to edit, and `create-invoice` reads it back. The edit endpoint (`Invoice/GetInvoicesList`) doesn't carry it. The new app replaces the localStorage hand-off with an `editable` query param passed from the list to the edit route (defaulting to editable when opened directly), and `IsEditable` is typed as `number` (0/1) in `InvoiceListModel` to match the backend.
- **No menu-grouping column exists at all** — **WRONG; superseded.** The `MenuItem` table has a `MenuGroup` column (`'Sales'` / `'Master Data'`) and it reaches the client via `MenuModel.MenuGroup` (see the corrected `MenuItem.CssClass` note above). No new column is needed; grouping is `ParentMenu.MenuGroup === 'Sales'` vs everything else.
- **`TAXInvoice.ConversionRate` is stored per invoice/quote but not selected by `GetInvoiceList` or `GetQuoteList`.** Needed for accurate multi-currency aggregate totals (see `BUSINESS-RULES.md`). Same SP → EDMX → `InvoiceListModel`/`QuoteListModel` → `InvoiceService.cs` mapping-loop chain applies.
- **`CommonController.GetSiteuserMenuList(int roleId)` instantiates `new EmqubeCommonService()` directly**, bypassing the DI-registered `ICommonService`/`CommonService` (from `EmqubeInvoice.BL`) that other controller actions use. Two parallel, differently-implemented "common service" concepts coexist in the old codebase — don't assume they're the same thing or that a change to one affects the other.
- **Quote "status" has no real signal.** `QuoteListModel` carries `PaymentRecdDate`/`PaymentRecdDateString` (unusual for a quote) and the underlying table has an unused `ExpiryDate` — neither has been confirmed to mean "customer responded / quote accepted." Verify against real data (compare a known-accepted quote to a known-pending one) before building any status feature on either field.
- **Endpoint response shapes are inconsistent across the API.** Some return a plain array (`Invoice/GetCustomerList`), some wrap in `{Error, ...}` (`Common/GetCountry` → `data["CountryList"]`). Check each endpoint's actual shape individually — don't assume consistency.

## CSS / frontend (useful context even though the new app gets fresh CSS — explains *why* certain rules will be needed again)

- **Bootstrap 3's `.modal-header::after` clearfix becomes an invisible flex item** once a modal header is given `display: flex` (as the design system's `.eq-modal` does) — it silently splits `justify-content: space-between` across three slots instead of two, stranding the close button off-center instead of flush right. Fix: `content: none; display: none;` on that pseudo-element wherever a flex modal header is built.
- **A dropdown/popout menu inside any scrolling ancestor** (e.g. a table wrapper with `overflow-x: auto`) gets silently clipped unless it's rendered outside that ancestor (`container="body"` in ng2-bootstrap's case; the CDK Overlay equivalent is attaching to a global overlay container, which it does by default — worth confirming this "just works" when the new `EqDropdown` is built, rather than assuming).
- **Native `<select>` option hover/highlight color is OS/browser chrome**, not something CSS can restyle in Chrome/Edge. Don't spend effort trying to brand it — a fully custom dropdown component is the only real fix if pixel-perfect branding on a select-like control is ever required.

## Old app dependency landscape (context for why the rewrite decision was made — not actionable for the new app, since none of this is being ported)

`package.json` in the old app carries duplicate/overlapping libraries for the same job: two toast libraries (`ng2-toastr` + `angular2-toaster`), two data-table libraries (`angular2-datatable` + `angular-4-data-table`), two pagination libraries (`ng2-pagination` + `ngx-pagination`), and a half-installed second Bootstrap integration (`ngx-bootstrap@2.0.0-rc.0` alongside the actually-used `ng2-bootstrap@1.6.1`). Plus: `@angular/http` (removed in Angular 8), RxJS 5-style operator-patch imports (`import 'rxjs/add/operator/map'`), TypeScript 2.2, Angular CLI 1.x config format (`.angular-cli.json`).
